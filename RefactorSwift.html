🔍 Why the Current Stack Has So Many Moving Parts

The friction you experienced (e.g. two icons in the Cmd+Tab app switcher, tabbing focusing a windowless process, needing activation workarounds) is the direct result of trying to make a Unix/Go command-line engine behave like a native NeXTSTEP/Cocoa application.

Current Architecture Go + Cgo + Swift + WebKit
1. Outer Wrapper Bundle (sqldoc.app) Swift binary (Launcher.swift) running a 1-second polling timer loop to catch Apple Events.
▼ Spawns via NSWorkspace
2. Inner Nested Bundle (sqldoc.app) Second full bundle in Contents/Library/ containing the Go viewer binary.
▼ Launches HTTP listener on 127.0.0.1:port
3. Go Backend + SQLite Driver (cgo / modernc) Goroutines for background counts, column widths, and keyset seek queries over HTTP JSON.
▼ Renders WebKit window & executes JS
4. Frontend (app.js / app.css) 900-line vanilla JS virtual grid communicating over localhost REST endpoints.
Pure Swift Architecture Native Swift / AppKit
1. Single Standard App Bundle (sqldoc.app) Native NSDocument or AppKit binary. Directly receives double-clicks via application(_:openFiles:).
▼ Direct in-process call (Zero IPC / Zero HTTP)
2. SQLite Engine (libsqlite3.dylib / GRDB) Direct C-API calls to system SQLite. Swift actor handles background counts & sampling asynchronously.
▼ Direct native memory binding
3. Native UI (NSTableView or WKWebView) Hardware-accelerated virtualized table view with zero serialization overhead and native trackpad physics.

⚖️ Pros and Cons of a Pure Swift Mac App

✅ The Advantages (Pros)

1. Perfect macOS Integration (Zero App Switcher Bugs)
No ghost launcher processes, no nested bundles, no 2-icon Cmd+Tab clutter. Native window tabs (Cmd+T), native Fullscreen / Split View, and standard macOS keyboard navigation work automatically.
2. No Localhost HTTP Server or Socket Ports
Eliminates ephemeral port binding, firewall alerts ("Do you want sqldoc to accept incoming network connections?"), and potential port collisions entirely.
3. Instant Startup & Tiny Binary
Uses macOS’s pre-installed libsqlite3.dylib and native frameworks. Binary drops from ~25 MB to ~3 MB, and startup time drops to single-digit milliseconds.
4. Deep Apple Ecosystem Features
Easily add Quick Look file preview extensions (press Spacebar in Finder to preview a .db without opening the app), Spotlight indexing for database schema, and macOS Shortcuts support.
5. Mac App Store & Notarization Simplicity
Standard Xcode project with automated hardened runtime, sandboxing, and Apple Notarization without custom shell scripts or ad-hoc codesigning workarounds.

⚠️ The Trade-offs (Cons)

1. Loss of Shared Cross-Platform UI
The current Go + JS frontend can run on Linux (WebKitGTK) and Windows (WebView2). Writing a 100% native SwiftUI/AppKit UI means maintaining two separate UI codebases if Linux/Windows support is needed.
2. Re-implementing the Virtual Grid
The ~900 lines of custom column resizing, keyset scrolling, dynamic row heights, and search filters in internal/ui/app.js must be rewritten in NSTableViewDataSource or SwiftUI.
3. CLI Tool Parity (sqldoc bench, sqldoc info)
If you still want a terminal CLI tool (sqldoc info file.db), you either need to keep a small Go CLI or build a Swift CLI companion binary.
4. Toolchain Dependency
Requires macOS with Xcode to compile. Cannot be easily cross-compiled from a Linux CI runner without specialized Docker macOS SDK tools.

🛣️ Two Potential Migration Paths

Recommended
Path A: 100% Native SwiftUI / AppKit
Complete rewrite in Swift using AppKit’s battle-tested NSTableView.
  • Zero WebKit overhead: Native Cocoa scrolling physics (inertial bouncing, smooth 120Hz ProMotion).
  • Peak Performance: Zero JSON serialization; database buffers bind directly to table cell views.
  • Cleanest UX: Native macOS menu shortcuts, contextual menus, drag-and-drop, and system dark mode.
  • Effort: ~1.5 - 2 weeks.
Path B: Swift Shell + Embedded WKWebView
Replace Go & HTTP server with Swift, but retain the existing app.js frontend.
  • Swift Native App: Single bundle, zero launcher hacks, instant Apple Event handling.
  • Keep Frontend: Reuses existing app.js, app.css, and virtual grid layout.
  • Direct JS-Bridge: Uses WKScriptMessageHandler instead of localhost HTTP.
  • Effort: ~2 - 3 days.

💡 Bottom Line Recommendation

If sqldoc is primarily intended to be a first-class Mac tool, rewriting it as a pure Swift app is relatively easy (~1 to 2 weeks) and completely eliminates 100% of the Mac integration bugs (Cmd+Tab duplication, launcher timeouts, window centering shims, and cgo thread locks).
